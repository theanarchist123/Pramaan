# What `alembic upgrade head` does (0003 -> 0012)

Measured, not guessed: `backend/scripts/migration_rehearsal.py` builds a scratch database at revision 0003 with data in it,
upgrades it, downgrades it, and diffs the schema and a fingerprint of every existing row. Re-run it any time:

```
docker compose up -d db
cd backend && .venv\Scripts\python scripts\migration_rehearsal.py      # ends with REHEARSAL PASSED / FAILED
```

**Result of the last run:** upgrade 0003 -> 0012 succeeded; **no existing row changed** (users, profiles, claims, review queue all
fingerprint-identical); a second `upgrade head` is a no-op; `downgrade 0003` restored a schema **identical** to the starting point
and the data identical. Caveat: the scratch database is *built to look like* production at 0003 (the 0003 schema plus sample rows),
not a copy of your live database. Take a Supabase backup before you run it there.

## Per revision

| Rev | Adds | Existing data |
|---|---|---|
| **0004** | `profiles.decision_basis` VARCHAR(12) NOT NULL DEFAULT `''`; `profiles.wikidata_qid` VARCHAR(20) NOT NULL DEFAULT `''` | Every existing profile gets `''` for both. Approved profiles show plain "Approved" (the system cannot know whether a person or automation approved them) |
| **0005** | The Procrastinate job queue: tables `procrastinate_jobs`, `_events`, `_periodic_defers`, `_workers`; 19 `procrastinate_*` functions; 7 triggers; enum types `procrastinate_job_status`, `procrastinate_job_event_type` | None touched. Created only if missing |
| **0006** | Table `llm_calls` (+ index on `run_id`) | None |
| **0007** | Table `image_assets` (+ unique `unsplash_id`, index on `sector`) | None |
| **0008** | Tables `user_roles`, `admin_audit_log`, `approval_requests`; function `admin_audit_log_immutable()`; trigger `admin_audit_log_no_change` (refuses UPDATE and DELETE) | None. **Nobody has a staff role afterwards**: legacy `users.role = 'admin'` keeps working (all permissions) |
| **0009** | `review_queue.assigned_to` UUID, `locked_until` TIMESTAMPTZ, `sla_due_at` TIMESTAMPTZ (all NULL-able); table `review_decisions` | Existing open cases get NULL for all three (no lock, no SLA clock) |
| **0010** | `users.totp_secret_enc` VARCHAR(300), `mfa_enrolled_at`, `stepup_until` (all NULL-able) | Everyone is "not enrolled" |
| **0011** | Tables `governed_settings`, `governed_setting_changes` | None: settings keep their environment values until someone changes them through an approval |
| **0012** | Table `mfa_recovery_codes` | None |

Nothing in 0004-0012 updates, deletes or rewrites an existing row, and nothing drops anything. All statements are `IF NOT EXISTS`
/ `checkfirst`, so re-running is safe.

## What cannot be undone cleanly

- **Data created after the upgrade is destroyed by a downgrade.** Each downgrade drops what its upgrade added, so rolling back
  deletes: the **audit log** (`admin_audit_log`, 0008), all staff **role grants**, approval requests, review decisions, **MFA
  secrets and recovery codes**, governed-setting overrides and history, approved sector images, recorded LLM calls, and **every
  queued or finished background job** (0005). Rolling back after real use is a data-loss event: export first.
- **The audit log is append-only by design**: the trigger refuses `DELETE`, so you cannot remove entries by SQL either; a downgrade
  works because it drops the whole table.
- **0001 (the baseline) cannot be downgraded** (it raises). The downgrade chain therefore stops at 0003 -> 0001 in practice;
  restore from backup to go further back.
- **0005's downgrade** was previously `NotImplementedError` (so no downgrade past it was possible). It now drops every
  `procrastinate_*` table, function and enum; fixed and covered by the rehearsal.
- **Existing databases created by the old `create_all`**: the baseline creates only missing tables; columns added after the fact are
  added by 0004, 0009 and 0010 with the `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements above.

## Before you run it on Supabase

1. Take a backup (Supabase dashboard -> Database -> Backups, or `pg_dump`).
2. Run the rehearsal locally; expect `REHEARSAL PASSED`.
3. `cd backend && python -m alembic upgrade head` (or start the API once with `AUTO_MIGRATE=true`).
4. Set `STAFF_MFA_REQUIRED=true` only **after** every staff member has enrolled and saved their recovery codes. It defaults to off.


## 0013 (added with TRU-08)
| **0013** | Column `certificates.status_index` (nullable integer) + unique index | None: existing certificates keep NULL until first requested as a credential, then get a random free index |

Downgrade: `ALTER TABLE certificates DROP COLUMN status_index` (removes the index or constraint with it; they differ between a database built
from the models and one upgraded from 0012, which is why the downgrade drops the column rather than the index). Rehearsal passes
(`tests/test_migration_rehearsal.py`): rows unchanged after upgrade and after downgrade, schema identical to the starting point.
The rehearsal script keeps a hand-maintained list of post-0003 columns (`ADDED_COLUMNS`): any future migration that adds a column must be listed there.

## 0014 (added with TRU-04)
| **0014** | Table `identity_bindings` (profile_id FK cascade, kind, subject, status, code_hash, challenge, target, attempts, expires_at, verified_at) | None: a new table only |

Downgrade: `DROP TABLE identity_bindings` (loses bindings, which are evidence the owners can recreate). Rehearsal passes; the rehearsal script's
`ADDED_TABLES` list now includes `identity_bindings`.
